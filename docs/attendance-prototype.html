Old-flow baseline: 10 people × 2 line items each = 20 rows, and every row costs four inputs — pick project · pick line item · pick task · enter hours. The new count is only what you actually tap in this prototype.

  1. One tap confirms the whole crew

    The schedule already knows who is at which site on which line item. Attendance is only confirm or correct — it should never re-ask for what dispatch already decided. One tap on Chen Residence posts five people’s attendance and their hours together.

    tap the amber button on the card

  2. Switch the work item, hours split themselves

    The line item hangs on the block of time, not on each person. When the crew changes tasks after lunch the foreman taps the new work item; the day splits in two and every crew member’s hours redistribute across both blocks. Zero extra input. Drag the boundary to adjust.

    tap DR-02, then drag the divider

  3. Log only the exceptions

    The foreman never tells the system who showed up — only who didn’t. Tap any avatar for late, left early, half day, personal, sick, or reassign. Absence is the rare event, so it should carry all the typing.

    tap Danny Pham’s avatar

  4. Drag a person to another site

    “I moved Javier over after lunch” is one motion on site, so it should be one motion here. Drag a crew chip onto another site card and the day splits, with each half costed to its own job. Keyboard users get the same result from Move to… in the sheet.

    drag Jorge Nava onto any site card
Office · Weekly review

Let the people who need precision add the precision

The field produces half-day accuracy, which is fast. Job costing wants exact allocation, which is slow. Don’t make those two needs fight on the same screen — move the fine-grained split into the office, once a week, in bulk, instead of asking a foreman in work gloves to pick a task code in direct sunlight.

The structural change underneath

Cost attribution belongs to the time block, not to each person

One tap can settle five people only because the line item is stored once. In the old shape, correcting one attribution means editing N rows — and missing one is exactly how a job-cost report drifts out of balance.

Today
attendance(
  person_id,  date,  hours,
  project_id, line_item_id, task_id
)

The attribution is duplicated N times, N = crew size. Foreman input scales as people × line items, and every copy is a chance to mistype or miss one.

Proposed
work_block(
  job_id, date, line_item_id, start, end
)
attendance(
  person_id, work_block_id, status, delta
)

Stored once. A person only carries presence and exceptions. Labor hours = block length × people present in it, costed to the line item automatically.

Rollout

Phase one cuts ~80% of the taps without touching the backend

Phase 12–3 weeks

Site cards, confirm-all, line item inherited from dispatch

The write layer expands one work block into per-person rows against the existing table. Reporting and payroll stay untouched, migration risk is zero, and the time saved is measurable in week one.

Phase 24–6 weeks

Persist work blocks, drag-to-reassign, weekly allocation

Attribution actually moves off the person and onto the block. This is the first step that needs historical migration, and it can go project by project.

Phase 3if needed

Geofence suggests; it never clocks anyone in

“5 people appear to be at the Danville site — confirm?” always stays a suggestion. Job-site positioning is noisy, and automatic clock-in invites both mistrust and a stream of manual corrections.
